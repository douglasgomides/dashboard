## What changed

- `chaveDaMensagemExistente(chaves, existentes)`: pure; messages present in `existentes` take that conversation key,
  others keep the key from `chavesConversaKommo`. Input map is not mutated.
- `gravarJanela`: the two reads it already does (lead conversations of the window's leads, legacy talk conversations)
  now also select `id` and fill `candidatas` (id -> externo_id). After that, `mensagens` is read with
  `.in("conversa_id", candidates).in("externo_id", window message ids)` (unique index `(conversa_id, externo_id)`),
  paged by 1000, same error handling (push + return). If a message is already in two candidates, the `lead:` one wins
  (ties by smaller externo_id). Comment in code explains why the lookup is per candidate conversation.
- Cleanup file: (a) read-only before; block `begin;` -> temp table of rows to delete (`on commit drop`) -> DELETE ->
  UPDATE of iniciada_em/ultima_msg_em of conversations that lost a row and still have messages -> DO checker that raises
  if any Kommo duplicate remains -> `commit;`; (d) read-only after, last statement of the file.

## Deviations from Plan

1. **[Rule 2 - Safety] Checker inside the transaction instead of "if (d) is not 0, run rollback".** In the Supabase SQL
   editor a pasted block runs to the end in one go, so João cannot look at (d) between DELETE and `commit;`. The block
   ends with a DO statement that raises if any Kommo duplicate remains; the raise aborts the transaction and nothing is
   written. (d) stays as a separate read-only section after `commit;` and is the last statement of the file, so
   pasting the whole file shows (d).
2. **[Rule 2 - Safety] Rows used by operacao_recuperacao are never deleted**, even when two copies are both used
   (that would be an FK error); that case is shown in (a) as `presas` and makes the checker roll back.
3. **[Rule 3] Lookup batches 100 x 100 instead of 200 x 200**, so the URL of the read with two `in` lists stays the
   size of the other single-list reads in the file (200 uuids). Paged by 1000 rows.
4. **Empty conversations keep their dates** (only conversations with remaining messages are recomputed), so no
   iniciada_em/ultima_msg_em becomes null; they are counted in (a) `conversas_que_ficam_vazias` and (d).
5. The required-reading file `03.1.1.1.1-04-SUMMARY.md` does not exist; that plan's summary is `s04.md` (its risk is
   restated in RESEARCH Achado 7, which was used).
6. Not run against production: no Supabase MCP tool was available to this executor, so the SQL was only run in PGlite
   (Postgres 16/17 via PGlite). Syntax is plain Postgres.
